The two options

Rigid — one skeleton

A hierarchy is made in PIM and pushed to F&O. F&O receives that same hierarchy. Rolly: with no mapping table, the push is one-to-one.

Same folders on both sides. A rename or a move in PIM rewrites the F&O folder.

Dynamic — two hierarchies and a map

PIM keeps its own folders. F&O keeps its own categories. A map links one PIM folder to one F&O category. Jay said that map could be a screen in PIM. A change on one side does not rewrite the other.

A move

Rigid

The folder moves in PIM. The same folder moves in F&O, because there is only one tree.

Rolly: purchase orders and sales orders store the category node the product was connected to. A report that uses the tag on the invoice still shows the old node. A report that uses the item’s current node shows only the new one, and the earlier year drops off that node.

Dynamic

The PIM folder can move without rewriting the F&O category. The map row is what changes.

The order tag is still Rolly’s concern. The map does not rewrite history on the invoice. It only says which F&O category the PIM folder points at now.

A delete

Rigid

Rolly: once a product is released and transactions exist, F&O cannot undo or delete that node. Deleting it in PIM does not delete it in F&O.

Dynamic

Jay: a delete removes the mapping. The F&O category stays when an order already uses it. Rolly’s delete block still applies on the F&O side.

Checked against what is already in Pimcore

  • The live catalogue is one tree under /ErpSyncLive. F&O sends it. The folder code stored on each node is the F&O record number.
  • Screws and washers are two classes, PtScrew and PtWasher. Both allow inheritance and variants. That is standard Pimcore. An empty field on a child shows the parent’s value.
  • Each field has one owning level. Head type is on the series. Material is on the range. Diameter is on the product group. Length is on the master. The master holds several allowed dimension values. The variant holds one.
  • /InheritDemo uses those same classes. It proved the inheritance. It did not add a second tree, a map, or a send back to F&O.
  • The feed writes a value onto the object named in the row. It does not turn folder inheritance on. The folder-default switch stays off.

Where inheritance sits

Inheritance fits the classes that exist. It does not choose rigid or dynamic. F&O does not inherit, so a value set on a series in PIM still has to be sent as that value on the item number. /InheritDemo is that picture, inside one PIM tree.

Which approach fits

RigidDynamic
The tree already in /ErpSyncLive Closer. That tree is already one hierarchy, keyed by the F&O record number. A push sends the same folders. Farther. A second shape, plus a map, does not exist. The first load can still be one-to-one, which Rolly said.

A later second ERP, which Jay mentioned Another one-to-one push, one skeleton per ERP. The same PIM tree, another map. That was Jay’s reason for this option. No AX flow was drawn.

Pimcore standards

Already standard, already in the classes

  • A folder tree, parent and child.
  • Inheritance when the child field is empty.
  • Variants under a master.
  • A classification store for the measures.
  • Relations: one value, or a list of allowed values.
  • The object id stays the same after a rename or a move. The path changes.
  • Publish and unpublish. Versions of the object.

Not a Pimcore feature

  • A connector that writes folders and values into F&O.
  • A map between a PIM folder and an F&O category.
  • A “send to F&O” flag on an attribute.
  • A call to Azure on save, or on a schedule. A scheduled command is normal PHP. The F&O call is not.
  • F&O’s rule that a category on an order cannot be deleted.

One tree plus inheritance is the versatile Pimcore part, and both options can sit on it. Dynamic adds a map. That map is the piece Pimcore does not already maintain. Jay said it could be a screen in PIM. Adil later proposed it lives in his Function App. If the map stays in the Function App, Pimcore’s job is still one tree, inheritance, and a send of the shown values.

If one option is chosen, what the current Pimcore can maintain

Rigid

  • Keep PtScrew and PtWasher, the five levels, and inheritance. No new class for the tree.
  • Add a scheduled send of those folders, then the value the master shows.
  • The first send can use the F&O record number already stored on the folder.
  • Pimcore can maintain the folders, the inherited values, the dimension lists, and the variants. That is what the admin already does.
  • Pimcore cannot maintain the order tag or the delete block. A move here becomes a move in F&O.
  • His current /tree and /product-attributes feeds must stop on an agreed date. Until then they overwrite a value typed in PIM.

Dynamic

  • The same classes and the same inheritance stay. /InheritDemo is still the shape of the values.
  • The map is new. It is not a field today. A link object can be built, or the map stays in the Function App.
  • A different PIM shape would be another root of the same class. Pimcore can hold that. The feed must not write it.
  • Someone has to maintain which PIM folder points at which F&O category. Pimcore has objects and relations for that only after the link is built. It has no mapping screen now.
  • The value send is the same as rigid: the value the master shows, on the item number.
  • The same feed-stop rule applies. Two writers on one value will fight.

What stays hand-built either way

  • A new attribute still needs a field and an alias before it appears, and before it can go back to F&O.
  • en-US wording on a pick-list is not copied into the imperial box. That gap is on the way in. It is not solved by either tree.
  • Danish and Swedish product names are not a return call. He marked that as not in v1.
  • There is no record of what was last sent, so a removed value cannot yet go back as deleted on that one attribute.

Judgment. Inheritance fits now, on the classes that exist, and it does not require either option. Rigid is the smaller change inside Pimcore and the worse fit to the order problem Rolly described. Dynamic matches that problem, and it is more work because of the map, not because Pimcore cannot inherit. If the map stays in the Function App, Pimcore maintains one tree and the inherited values for either choice. It does not maintain F&O.
