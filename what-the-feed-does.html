What the F&O feed does

29 Sep 2026. What Pimcore stores, and the order the feeds have to arrive in. This page does not describe request bodies.

What is happening

F&O pushes the catalogue into Pimcore. Pimcore does not read F&O. Each feed creates or updates one kind of thing: a company, a folder, a dimension value, a product, a product’s attributes, a product’s names, or the shops that sell a variant.

The point of the feed

Folders say where a product sits and which attributes apply there. The product itself holds the values, the name, and the shops. Two products under one folder keep their own values.

Sending the same business key again updates that same object. It does not create a second one. A missing parent does not get invented: that row fails, and the rest of the batch still applies.

Order

On a first load, run them in this order. After that, send only what changed, and only after the thing it hangs on already exists.

  1. CompaniesThe legal entities. Independent of the catalogue.
  2. DimensionsThe colour, size, config, and style lists. A variant can point at these only after they exist.
  3. TreeThe five folder levels. Parents before children.
  4. Attribute setupWhich attributes exist, how they are grouped, and which folder uses which group. Not the values.
  5. ProductsMasters on the lowest folder. Variants on their master, after that master exists.
  6. Attribute valuesEach product’s own values. The product must already exist.
  7. NamesThe product’s names. The product must already exist. Can run before or after attribute values.
  8. ShopsWhich companies sell a variant. The company and the variant must already exist.

A key check and a reachability check exist. Neither one writes catalogue data.

The catalogue

One class runs from the top folder down to the variant. Level 1 chooses screw or washer. Children keep that choice. A folder’s level cannot be changed after it is created. Moving it under another existing parent is allowed. Giving it a new identity creates a second folder and leaves the old one in place.

VariantThe sellable item. Shops hang here.
MasterThe product the variants belong to.
Product groupThe folder a master hangs on.
RangeFolder. Says which attributes apply.
SeriesFolder. Says which attributes apply.
FamilyFolder. Brand is accepted and is not being sent.
TypeScrew or washer.

Companies

Any company code is stored as a legal entity. Creating the company does not put the product in a shop. Four codes can later become a shop on a variant: RH, RHU, ASW, and SPI. Any other company can still be released to, and it does not get a shop brick. Unpublishing a company does not delete it.

Dimensions

Configuration, colour, size, and style are lists of values. Each value is its own object, matched by its code. A variant points at one value from each list it uses. The code has to stay stable. Sending the same code again updates that value. A code that already belongs to the workshop catalogue is reused and its workshop name is left alone.

These lists are not product attributes. Diameter, length, head type, material, and coating are attributes. They are not sent here.

Tree

Five folders, from product type down to product group. The level-1 folder must say screw or washer. Anything else is skipped and the folder is not created. Children do not repeat that choice; they inherit it. An empty brand or an empty product-group number still creates the folder.

Brand on the family is accepted. It is not part of the current send. Pimcore does not copy the folder name into the brand.

Attribute setup

This feed describes the attribute book. It does not put a value on a product. It says which attributes exist, which type each one is, which options a list has, which attributes sit in a group, and which folder uses which group.

The folder assignment is what decides whether a later product may carry that attribute. A product only receives an attribute when one of its ancestor folders uses the attribute’s group. The assignment is the list. It is not the value.

Send it when the book changes, not once per product. Leaving an attribute or a group out of a later send does not remove it. There is no delete for an attribute or a group yet. Sending a list attribute’s options again replaces that attribute’s option list. Sending an empty group list for a folder clears that folder’s assignment, so products under it no longer receive those attributes.

The code you define is the code you must send later, including spaces and letter case. Pimcore stores that text as sent, after trimming the ends.

Products

A master hangs on a product-group folder. That folder decides screw or washer. A variant hangs on its master. The variant is the thing a shop can sell. A master alone cannot be released to a shop.

A sellable product that has no variants

Send the master, and one variant with the same number. Do not invent a second number, and do not fill config, colour, size, or style. Empty dimensions mean this product has no dimensions. That variant is enough for a shop to attach to.

A master that has no variants yet

Send the master only. Do not create a variant until the real variants exist. A shop row for that master number is not found, because no variant carries it.

A real variant sends the dimension codes it actually has. Those codes must already exist in the dimension lists, and they must be allowed on that master when the master has a list for that axis. An unknown code does not fail the variant; that axis is left unset.

The master’s allowed lists are sent on the master. They are not guessed from the variants. An empty list does not restrict that axis.

Attribute values

Each value is stored on the product the row names. If that number is a variant, the value is stored on the variant. If no variant has that number, it is stored on the master. Nothing in this feed is written onto a folder.

The folder assignment from setup only answers one question: does this product’s branch include this attribute? If not, the value is not stored. If yes, the product keeps its own value. A second product under the same folder does not replace the first. Clearing a value clears that product only.

Head, material, coating, diameter, and length all follow that rule. A code that has no catalogue field yet is still kept on that same product. A unit that is left out keeps the unit already stored. A list value has to be one of the options from setup.

If an older copy of the same value is still sitting on a folder above the product, that folder copy is removed when the product row is applied. Otherwise every product with an empty field would still show the folder’s value.

Names

en-CA is the language that fills the product’s name. That is the same name the product feed can set, and the later write wins. The en-CA description is stored on that same product. It does not fill the name, and it does not fill the shop description.

Every other language, both name and description, is stored on that same product. The language code is kept as sent. en-CA and en-ca are not the same code. Only en-CA fills the name field. A language that is left out of a later batch is kept. The shop text typed in Pimcore is never changed by this feed.

When a variant exists with that number, the texts are written on the variant. They are not copied onto the master.

Shops

One row says whether one variant is sold by one company. true adds that company. For RH, RHU, ASW, and SPI it also turns on that shop. Any other company is recorded on the variant and does not get a shop. false removes that company, and removes that shop when the code is one of the four. Silence does not remove a shop. Stopped-for-sales is not read from this flag.

The row has to name a variant. A master that has no variant with the same number is not found. A variant Pimcore has never held is not found either. Sending false for a variant and company that were never linked, when that variant does exist, changes nothing.

Repeats, clears, and removal

What you doWhat Pimcore does
Send the same key againUpdates that object. Does not create another.
Leave a field outKeeps the stored value.
Send an empty valueClears that value.
Mark a company, folder, or product deletedUnpublishes it. Does not hard-delete it.
Leave an attribute or a group out of setupLeaves it in place. Setup has no delete yet.
Clear one product’s attributeClears that product only.

A batch that is too large is refused as a whole. Split it and send the pieces. There is no rate limit on these feeds. A row that fails does not roll back the rows that succeeded.

Not in this version

Barcodes, pack size, and relations between products are not stored. Brand on the family folder is accepted and is not part of the current send. There is no production address yet. The behaviour on this page is what the current Pimcore feeds do.
