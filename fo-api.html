Order & rules

One tab = one POST body. Do not mix fields between tabs. On a first full load, run the numbered feeds top to bottom. After that, send only what changed, but never before its parent exists in Pimcore.

Before any batch

/auth or /ping — optional smoke test. They do not create catalogue data.

Feed order (what must exist first)

#POSTNeeds firstWhy
1/companies—Legal entities. Independent of the catalogue tree.
2/dimensions—Colour, size, config, style lists. Variants on /product-master point at these codes.
3/tree—Five folder levels. Parents before children. Level 1 06 or 09.

One line: companies → dimensions → tree → attribute-definitions → product-master → product-attributes → product-translations → product-release.

Inside one batch

  • /tree — parent folder before child.
  • /product-master — master row before its variants.
  • Other feeds — order inside the batch does not matter; match keys are per row.

Rules for every write

RuleBehaviour
Match keyBusiness key, never a Pimcore id. Re-sending the same row updates in place, so retries are safe.
Omit a fieldKeep the current value. This is the only way to say "no change".
null, "", or spaces onlyClear the value. An empty string is not "no change".
isDeleted: trueUnpublish that object. Never a hard delete. It only applies to an object this feed creates — see /product-translations.
Missing parentThat row fails and is retryable. The rest of the batch still applies. We do not invent parents.
First run vs deltaFull set per feed in the order above, then changed rows only.

How Pimcore will use this

  • Placement is folderGroups, not a hardcoded layer table. A later category is another folder and another group on the same call.
  • A brand-new product class still has to exist first. This payload cannot invent a class. Unknown product types stay skipped (06 screw, 09 washer).
  • The group code DIMENSIONS is not the existing POST /dimensions call. /dimensions remains only config, colour, size, style.
  • Danish and Swedish shop copy stays PIM-owned.
  • The folder you name is the branch. A known field is written on the object in that branch that owns it. It is not moved upward onto a folder you did not name. Length is written on the master under that branch, because each master has its own length.
  • Corrosion category sits on the Range, with material and coating. Send that group on the range folder. The catalogue icon is a Pimcore upload, not part of this call.

The setup call is now POST /attribute-definitions: definitions, groups, and folderGroups in one body, sent only when setup changes. A later category is another folder and another group on that same call. The payload cannot invent a product class that does not already exist.

/units — hold

Measure units such as mm and inch already sit on the Pimcore measure field, so a conversion table is not needed for the catalogue. Pack size — a box of one hundred — is a real shop fact, but there is no field for it in Pimcore today. If Red Horse wants it, we add the field first.

/barcodes — hold

There is no barcode field on the product classes. Not a refusal: model it, then feed it.

/relations — hold

Accessory, alternative, and spare part are not fields today. The one product-to-product link that exists is the washer on a style-W screw, which belongs on /product-master. Cross-sell is a Red Horse decision first.
