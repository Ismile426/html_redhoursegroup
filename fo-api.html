Order & rules

One tab = one POST body. Do not mix fields between tabs. On a first full load, run the numbered feeds top to bottom. After that, send only what changed, but never before its parent exists in Pimcore.

Before any batch

/auth or /ping — optional smoke test. They do not create catalogue data.

Inside one batch

  • /product-master — master row before its variants.
  • Other feeds — order inside the batch does not matter; match keys are per row.

LIVE POST /api/v1/tree

Five folder levels. Your keys work. Three fields decide what Pimcore can fill on each level.

Required by the live API today: productType "06" or "09" on every level-1 row. It only picks the Pimcore class (screw vs washer). It is not the folder’s sort prefix and it is not categoryKey. Red Horse wants the visible 06 prefix removed so sort order can change — that is fine on name. Do not change categoryKey after create: the API matches on it, so a new id creates a second folder and leaves children and products pointing at the old one.

When something is off

For example, a variant with colour 99 that was never sent on /dimensions is still created. Its reply row carries "ignored": ["colour \"99\" unknown — send it on /dimensions first"].

You sendWhat happens
parentKey that is not a level-5 folderRow fails, VALIDATION, not retryable. Masters only hang off a product group.
masterItemNumber we have not seenRow fails, NOT_FOUND, retryable. Send the master and repeat the row.
A dimension value not yet on /dimensionsVariant is still created. That one dimension is left empty and named back to you under ignored. We do not invent a label.

config / colour / style on a washerWashers only carry size. The others come back under ignored rather than being silently dropped.

LIVE POST /api/v1/attribute-definitions

This is setup: what an attribute is, which group it belongs to, and which /tree folder (categoryKey) uses which group. Send it only when setup changes, never per product. Send /tree first — a categoryKey we have not seen fails that folder row and is retryable. The attribute rows in the same batch are still stored.

Use RH_Head, not HEAD TYPE. Same pattern for the other RH_ attributes we already saw: RH_Drive, RH_Point, RH_Coating, RH_Thread, RH_SpecialFeatures. DIAMETER, LENGTH MM, MATERIAL TYPE, and DRILL CAP MM stay under those names.
FieldRequiredRule
attributes[].codeYesStable F&O attribute code. This is what /product-attributes will send as attributeCode.
attributes[].dataTypeYestext · decimal · integer · boolean · list.
attributes[].unitNoSend on a decimal. Omit on a word.
attributes[].texts[]NoLabel per languageId. Stored as sent (en-CA, en-US, en-HK, and later ones). Not folded into en. These are attribute labels, not the product name.
attributes[].options[]On a listWhatever option codes you put here are valid. Empty option texts: the code is the label. Examples below are not a list we invented.
groups[]YesA named set of attribute codes. A later category is another group on this same call — no new endpoint.

LIVE POST /api/v1/product-attributes

Renamed from /attributes. This is the value on an item that already exists from /product-master. An unknown item fails that row and is retryable. An unknown attribute code, an option that is not on the definition, or a diameter that contains / is listed in ignored and does not fail the row.

Use RH_Head, not HEAD TYPE. Same pattern for RH_Drive, RH_Point, RH_Coating, RH_Thread, RH_SpecialFeatures. DIAMETER, LENGTH MM, MATERIAL TYPE, and DRILL CAP MM stay under those names.
FieldRequiredRule
itemNumberYesThe master code or the variant number that already exists from /product-master.
attributes[].attributeCodeYesMust match attributes[].code from /attribute-definitions.
attributes[].valueYesA list value is stored only when it is one of the option codes from the definition. A DIAMETER value containing / is skipped (range); a single number can be stored.
attributes[].valueToNoOptional upper bound when the definition is a from-to decimal (drill cap).
attributes[].unitNoSend on a decimal. Omit on a word.
attributes[].isDeletedNotrue clears that attribute only. It does not unpublish the product.
