Why your /translations feed does not land

  • F&O languages are en-CA / en-HK / en-US / zh-Hant. PIM sells in en / da / sv. F&O has no Danish or Swedish to send.
  • Your feed sends four English variants + Chinese into a field set that has one of them and needs two it can’t supply.
  • The one thing F&O could usefully give — a canonical English product name — is a single field, so it rides on /products, no separate feed.
If Red Horse wants F&O to drive per-language product names (not just shop marketing), then: (1) F&O must actually hold da/sv, and (2) PIM adds a localized name field to the class. Both are changes to agree first — not something to build on today’s model. Flag it and we cost it.

DROP the feed — groups still matter Attribute groups

Your confusion is fair, so here is the split. Attribute groups absolutely exist and matter. But there are two different things and only one of them is an F&O feed.

Attribute setup (your /attribute-setup)Attribute values (/attributes)
WhatDefinitions, data types, pick-lists, groups, and which folder/layer uses which groupOne item’s actual value: Head type = Torx
Who owns itPIM — set once in the classF&O — sent per item
How oftenOnce (changes on a schema change)Every product run

Why F&O does not send the setup

In this model, which group sits on which layer is fixed in the class: Product-Group measures on the Product Group tab, Master measures on the Master tab, Range geometry on the Range tab. The class says literally “groups for this layer only, children inherit, cannot add/remove groups.” It is not chosen per folder at runtime.

Your folderGroups[] (“folder X uses groups A, B”) assumes F&O assigns groups to folders. If F&O sent that nightly, it would try to redefine PIM’s schema and duplicate our locked groups.

Real open question (Kalle, C11): do different product groups need different attribute sets beyond the fixed per-layer model? If yes, that is a PIM modelling change we make once — still not an F&O feed. F&O keeps sending values only.

What is not an F&O feed — and why

Split into DROP (F&O is the wrong source), HOLD (no field yet — RH must decide), and one gap we do owe you (assets).

DROP /units (PCS / BOX, factor 100)

Order/packing quantities. Pimcore is not the order system; price and stock already stay out. Catalogue measure units (mm / in) already sit on the CS key. Send Length as F&O stores it ("35.00 mm") on /attributes; we parse it.

HOLD /barcodes

There is no barcode / EAN / GTIN field on PtScrew / PtWasher. Not a “no” — a “model it first.” If Red Horse wants EAN in PIM, we add the field, then take the feed. Your own HTML lists this area as open.

HOLD /relations (accessory / alternative / sparePart)

Those types are not fields today. The one product-to-product link we have is washerProduct on a screw SKU (“with washer”). Cross-sell/related is a real shop feature — but it is a modelling decision with Red Horse, then a feed. Not v1.

GAP Assets — images & compliance documents

This one is on us, not you. The classes already have technicalImages, labelImages (image galleries) and complianceDocuments (certificates / CE / ETA). Your HTML flags images and certifications as open too. So we will need a media feed or asset references — where does F&O hold the files (URL? blob? DAM?). Bring that and we design it.
