Approach 2 — how it works

30 October 2026. One example on TEST 10.100.16.4:82. The field rules are approach-2-flow.html and approach-2-api.html.

Two trees. F&O keeps its categories. PIM keeps its folders. POST /tree does not create a PIM folder. The only join is one category id stored on one product group. PIM does not post folder events back. F&O reads.

The same example, in order

1

F&O posts Send the category

POST /api/v1/tree. PIM stores a pick-list card. The catalogue folder is not created and not renamed.

{ "categoryKey": "5637165576", "name": "PG | 7500", "layer": "productGroup", "level": 5 }

Reply store is categoryPickList. linkedFolders is empty until a product group stores that id.

2

A person Build the PIM folder, then store the id

The person creates type, family, series, range, and product group under /ErpSyncLive/Catalog. The id is stored on the product group, in the admin field or by POST /api/v1/fo-category-key.

{ "folderId": 6713, "categoryKey": "5637165576" }

folderId is the PIM id from GET /fo-tree-links. It does not change when the folder moves. An empty id is rejected. A second id for the same folder replaces the first. The same id on two product groups is refused.

3

F&O posts Send the attribute book

POST /api/v1/attribute-definitions before any values. It stores codes, types, and which folder uses which group. It does not add a field to the screw or washer class.

4

F&O posts Send the master

One call, two results. The split is whether parentKey is the id on exactly one product group.

No folder yet — 88001

{ "code": "88001", "name": "Waiting master" }

Waiting card under /ErpSyncLive/Unassigned. Not a screw and not a washer. First reply: action held, layer unassigned. It is not a row on the product lists.

A variant, a translation, an attribute value, or a shop release for 88001 is stored and comes back held, with no layer. The last of each is kept. They are applied when the card is placed, in this order: variant, translation, attributes, release.

Linked — 40100

{ "code": "40100", "parentKey": "5637165576", "name": "Hex head roofing screw" }

Catalogue master under product group 6713. The folder decides screw or washer. Reply action created, layer master. Send the non-empty name on this row. On later rows, leave the name key out. PIM does not lock it: a later row that still has the name overwrites it.

A variant goes in the same batch, after the master: itemNumber, masterItemNumber 40100.

5

A person or F&O Place the waiting card

Two ways, same master. A later POST /product-master for 88001 with parentKey 5637165576 creates the catalogue master. Reply created. Keep the non-empty name on that row, then leave the name key out. Or a person places the card on the product group. That save returns nothing to F&O, so the name cannot be stopped on the place. A later row that still carries the name overwrites it. PIM does not lock the name.

6

F&O reads On F&O’s clock

PIM does not run a timer and does not call F&O. Read every page. Page size is 500. Compare the rows with count. After 40100 is a catalogue master, the lists show this.

GET /fo-tree-linksOne row per catalogue folder. 6713 has foCategoryKey 5637165576. foMap false does not hide it. A rename or a move is this compare. PIM sends nothing for it.
GET /fo-attributesThe attribute book: code, type, unit, options. A new class field appears only after it is deployed.
GET /fo-product-valuesMasters only, including unpublished. 40100’s row has categoryKey 5637165576. A value can come from the product group when the master does not store one. There is no marker. Decimal 0 is "0". A false boolean counts as empty.
GET /fo-product-placementitemNumber 40100, folderId 6713, foCategoryKey 5637165576. folderId is the parent folder.
GET /fo-product-enrichmentOn TEST. Not one of the four lists. Masters and variants. Names and descriptions. Inheritance is off, so an empty variant name does not show the master’s name. No image.
GET /fo-attribute-mapDo not call. F&O does not need a split between a folder value and a master value.

The one write that changes the next read

The values read shows RH_HEAD = HX on 40100 because product group 6713 stores it and the master does not. There is no marker on that value. Leave RH_HEAD off the master row. Sending HX stores it on the master, and a later edit of the folder is then not used for that code.

{ "itemNumber": "40100", "attributes": [ { "attributeCode": "LENGTH MM", "value": 100, "unit": "mm" } ] }

This row is right only when LENGTH MM 100 mm is not the value the read returned. If the read already showed 100 mm from the folder, leave that code out too. A variant itemNumber is found before a master code.

What this approach does not do

No folder from /tree. The pick-list card is not the catalogue.
No PIM post. The return URL is empty. Held rows are not sent.
No image, price, or stock on these reads.
Unpublish is not a delete. isDeleted: true on 40100 unpublishes it and leaves the object. The row stays on the product lists.

Shop codes on release are RH, RHU, ASW, and SPI. Kalle has not signed them. 6712 still has no id, so a master in that folder has an empty categoryKey.
