Shared rules

  • Header X-API-Key on every /api/v1 call. No key is HTTP 401.
  • Feed body { "batchId", "items": [] }. Unknown extra keys are ignored.
  • More than 500 items, or a body over 2 MB, is HTTP 413. Nothing in that batch is applied.
  • A bad JSON body is HTTP 400. A row that fails inside a valid batch is still HTTP 200. ok is false when failed is above 0. results has one entry per row. errors repeats the failed rows.
  • POST /fo-category-key is one object or { "items": [] }. It has no 500-row cap in the writer. An empty categoryKey is rejected. It cannot clear an id. It does not tick foMap. A different categoryKey for the same folderId replaces the stored id. The old id is not kept.
  • Reads: ?page=. Page size 500. Page below 1 becomes 1. Past the end, items is empty and count stays the whole list. Last page is page == pageCount. No cache. No rate limit. A read during a save can still show the previous row. The next read after the save finishes shows the change.

1. Categories — POST /api/v1/tree

Switch 1. Every accepted row writes the pick-list card. The catalogue folder is untouched. layer and level may both be omitted. When sent, layer is type, family, series, range, or productGroup. level is 1 through 5 and must agree with layer. master and variant fail. isActive is stored and does not block a link. isDeleted: true unpublishes the card. isDeleted: false, or a later row that omits it, does not publish that card again.

2. The link — person or POST /api/v1/fo-category-key

folderId is the PIM object id from GET /fo-tree-links. It stays the same when the folder is moved. parentFolderId changes on the folder that moved. path changes on that folder and on every folder inside it. A folder inside the one that moved keeps its own folderId and its own parentFolderId. A delete and a new folder gets a new folderId. FolderId and CategoryKey are accepted as well as folderId and categoryKey.

  • Missing or non-positive folderId: VALIDATION, not retryable, folderId is required.
  • Blank categoryKey: VALIDATION, categoryKey is required.
  • Not a catalogue type, family, series, range, or product group: NOT_FOUND, folderId is not a catalogue folder.
  • Same id already on another product group: VALIDATION, F&O category {id} is already stored on {path}. One product group, one F&O category.
  • The same id written again is still updated.
  • A different id for the same folderId replaces foCategoryKey. The folder id does not change. The next GET /fo-tree-links shows the new foCategoryKey. The old id is not stored on that folder and is not written onto another folder. A PIM move does not do this by itself. Only this post changes the stored id.
  • That replace fails when the folder is a product group and the new id is already on a different product group. The row is VALIDATION and the old id stays.
  • Folders above product group are not in that duplicate check. An id on a type, family, series, or range does not place a master. parentKey reads only the product group.
  • Setting or changing the id on a product group holds one link row and one placement row per master already in that group. Those rows are not posted. A rename or a move that keeps the same id holds nothing. Clearing the id removes the link table row and does not tell F&O to delete a category.

4. Waiting cards and how a placement shows up

The card lives at /ErpSyncLive/Unassigned. It is not a screw and not a washer. It is not a row on GET /fo-product-values or GET /fo-product-placement.

While it is a card, a variant, a translation with texts, an attribute value, or a shop release is stored in fo_unassigned_hold. The reply is:

{
  "key": "35032-V1",
  "action": "held",
  "note": "master 35032 is a waiting card; the row is stored and will be applied when it is placed"
}

A newer row for the same variant, translation, attribute code, or company replaces the stored one. isDeleted: true on a held variant replaces that payload and the reply stays held. It does not return unpublished. isDeleted: true on the waiting master unpublishes the card and drops its held rows. isDeleted on /product-translations is ignored. CONFLICT is not held.

Two ways the card becomes a master

  • A later POST /product-master with a parentKey that resolves. PIM saves the master, unpublishes the card, and moves it under /ErpSyncLive/Unassigned/Placed. Held rows then run in this order: variant, translation, attribute values, release.
  • A person places the card onto a product group in PIM. The folder’s class decides screw or washer. The card is marked placed. Held rows run in the same order. If that product group already has an F&O id, one placement row is held and not posted.

5. Attributes

Book — POST /api/v1/attribute-definitions

Send this before values. It stores codes, types, texts, options, groups, and which folder uses which group. It does not add a field to the screw or washer class. A new class field is a PIM developer change, then a deploy. Until that field is in the alias list or the classification store and the class has it, GET /fo-attributes does not grow.

dataType is text, decimal, integer, boolean, or list. Relation options become cards under /ErpSyncLive/AttributeOptions. Select lists and quantities do not. An existing option card is not renamed. Options include unpublished cards, and the read has no published flag, so every option code on GET /fo-attributes is a valid value.

folderGroups[].categoryKey is the F&O id stored on the folder. No folder: NOT_FOUND, retryable, no PIM folder is linked to category {id}; a person must store it in F&O category on the folder. Two folders: CONFLICT, not retryable, categoryKey {id} is stored on N folders in PIM; a person must leave it on one. This call accepts any catalogue folder that is not a master.

Values — POST /api/v1/product-attributes

Send itemNumber or categoryKey, not both. categoryKey uses the same id lookup. The folder must be a series, a range, or a product group, or the row is VALIDATION: categoryKey must be a series, range, or product group. A value whose code is not in the book is ignored: is not in /attribute-definitions, action unchanged. A value whose group is not on that product’s folder is ignored: is not placed on a folder of this item. Null, "", a text value that is only spaces, or isDeleted: true clears that code on the object the row names. Leaving the code out does not clear it. A clear on the master does not clear the folder. A clear on the folder does not clear the master.

A folder row stores a default on that folder, and only for a code placed on that folder. A code placed only on a parent folder is ignored. An itemNumber row stores the code on the object that number finds. A variant itemNumber is found first. Otherwise the number is a master’s code, and the value is stored on the master. It is not stored on the folder. The comparison is the value stored on that object. Pimcore’s inheritance switch is off for that comparison. A folder-only value counts as empty, so sending it stores it on the object. A code a person owns in Pimcore is not overwritten. A code that is not placed on a folder of that item is ignored.

GET /fo-product-values is masters only, including unpublished. This read turns Pimcore’s inheritance off, then walks the master and the catalogue folders above it, up to 20. An attribute is code, value, and unit. There is no source and no inherited flag. categoryKey is the immediate parent’s id. It does not say the value came from a folder. A stored decimal 0 is the master’s own value. The folder is not used for that code. An unset decimal is left out. A list is not mixed. If the master has any value for that code, the folder’s values are not added. A false boolean counts as empty, so a true on a folder above can be returned as "true". Empty text is left out.

Leave a code off the master row when F&O still has the value that read returned. For a decimal, that is the number and the unit. Sending the returned value with that master’s code stores it on the object the number finds. A variant itemNumber is found before a master code. When it lands on the master, and the master did not already store it, the next read uses the master’s own value. A later edit of the folder is then not used for that code. A stored boolean false does not do that. The next read treats false as empty, so a true on a folder above can still be returned. Send the code when F&O has a different non-empty value. A decimal sent without a unit is stored with the attribute’s unit, or with mm when the attribute has none. A missing unit is not a reason to send the code.

A waiting card with at least one attributeCode is held. A product that is neither a catalogue item nor a waiting card is NOT_FOUND, retryable: itemNumber not found; send it on /product-master first.

6. Text, shops, and what is not on the reads

POST /product-translations. en-CA name writes name. en-CA description writes descriptionMetric. en-US name writes nameImperial. en-US description writes descriptionImperial. Other languages write foTranslationBag. This call removes a leading language tag from the en-CA name on a master, and from the en-US name on a master and on a variant. Descriptions are trimmed only. POST /product-master does not remove that tag. A person can edit the stored fields. The next translation row overwrites the language and field it includes. A field left out stays. Null or "" clears the one sent. A person edit does not lock the field. There is no mark of which texts a person changed. A non-empty texts list for a waiting card is held. isDeleted on this call is ignored. These texts are stored. They are not on GET /fo-product-values. They are on GET /fo-product-enrichment, and that read does not remove a language tag.

POST /product-release. released is required, true or false. released: true adds the company. For RH, RHU, ASW, and SPI it also sets shopOn true on that shop brick. lifecycleState "3" with released: true still turns the shop on. released: false removes the company, sets shopOn false, and keeps the hero image and the description. A bad lifecycle state is VALIDATION and changes nothing. A release for a waiting card is held. After the variant exists, a missing variant is NOT_FOUND. Shop codes are those four. Kalle has not signed them. Star Fasteners has a brick and no F&O code.

There is no image URL. Hero is per company, on the shop brick, only when that brick is on the product. Screw technical images are a gallery on the product group. Screw label images are a gallery on the master. A washer does not have those two galleries. Search name, weight, pack size, barcodes, related products, and brand-per-company are not fields on these lists. Brand on a family is the en-CA friendly name from /tree, and it is not on GET /fo-tree-links.

GET /fo-product-enrichment is on TEST. It is not one of the four lists. One row per catalogue master and one row per catalogue variant, including unpublished. A waiting card is not a row. A held translation is not a row until it has been applied. itemNumber is the master’s code or the variant’s itemNumber. layer is master or variant. texts uses the same language ids as POST /product-translations. en-CA is name and descriptionMetric. en-US is nameImperial and descriptionImperial. Every other language is foTranslationBag. These are not the Pimcore language tabs. An empty name or description is left out. A language with neither is left out. A product with no text is still a row, with no texts. This read turns inheritance off. A variant with an empty name does not show the master’s name. It does not remove a leading language tag. A deleted product is absent. There is no image field.

Do not call GET /fo-attribute-map. It is not one of the four lists, and it is not the enrichment read. F&O does not need a split between a value stored on a folder and a value stored on a master. GET /fo-product-values is the value the master shows.

Folder scenarios

These are F&O’s own list. PIM does not send a folder create, a rename, a move, or an unpublish. Read GET /fo-tree-links every run and compare it with the last read. The same folderId is the folder. parentFolderId, path, and name are what changed. foCategoryKey changes only when a person or POST /fo-category-key stores a new id.

The only PIM call for a folder is POST /fo-category-key, after F&O has created the category. That post writes the new F&O id onto folderId. If that folder already has an id, the posted id replaces it, except the product-group clash above.

QuestionAnswer
Does /tree create the PIM folder?No on TEST. It stores the pick-list card.
Does folderId change on a move?No. parentFolderId changes on the folder that moved. An inner folder keeps its own parent id. Paths change.
Who stores the F&O id?A person, or POST /fo-category-key. The call does not tick Map to F&O. The tick does not decide parentKey.
Tick Map to F&O on the 8 groups for the folder test?No. Read foCategoryKey. foMap false means the box is unticked.
Does an id on a folder above the product group place a master?No. parentKey reads the product group only.
Is another product type one skipped reply?No. No parentKey is a waiting card. A token other than 06, SCREW, SCREWS, 09, WASHER, or WASHERS fails VALIDATION. A token for the other class fails CONFLICT.
Names, descriptions, images as a fifth list?GET /fo-product-enrichment is on TEST. It is not one of the four lists. Masters and variants. No changed-text mark. No image URL. Inheritance is off. The next translation send still overwrites the field it includes.
A rename or a move made only in F&O?PIM sends nothing. The next GET /fo-tree-links is the compare. A rename stays. Do not copy the folder name. If F&O applies parentFolderId, an F&O-only move is put back when the parent row has an foCategoryKey. The move does not change the stored id.
A second POST /fo-category-key with a different id?Yes. It replaces foCategoryKey on that folderId. The old id is dropped. If the folder is a product group and the new id is already on another product group, the post fails and the old id stays.
How often does PIM return data?It does not post. F&O reads four lists. GET /fo-product-enrichment is also on TEST and is not one of those four. Do not call GET /fo-attribute-map. There is no rate limit and no cache.
Does a new attribute code appear on the next GET by itself?A new class field has to be in the attribute list and deployed before GET /fo-attributes shows it. GET /fo-product-values shows a value stored on the master, or the nearest catalogue folder’s value when the master has none. There is no marker. Do not call GET /fo-attribute-map for a per-node split.
Unpublished option, unpublished master, missing master, boolean?An unpublished option code is valid. An unpublished master stays on both product lists. A deleted master is absent, not a clear. A boolean is sent only as true.
