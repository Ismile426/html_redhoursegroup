SWITCH 1 FOR parentKey POST /api/v1/product-master

Every other field on the current product page still applies. Two create paths:

No folder yet. Omit parentKey, or send JSON null. The master is a waiting card under /ErpSyncLive/Unassigned. It is not a screw and not a washer. productType is not read. Do not send "0", "06", or "09" to choose a class. None of them do.
Folder already linked. Send parentKey as the F&O category id a person stored on one product-group folder. That folder decides screw or washer. Omit productType, or send JSON null. If you send it, it must match the folder.

Example — one waiting master, one linked master, then its variant

{
  "batchId": "a2-master-001",
  "items": [
    { "code": "88001", "layer": "master", "name": "Waiting master" },
    { "code": "40100", "layer": "master", "parentKey": "5637150105",
      "name": "Hex head roofing screw 6.5 x 100" },
    { "itemNumber": "40100", "masterItemNumber": "40100", "layer": "variant",
      "name": "Hex head roofing screw 6.5 x 100" }
  ]
}
  • 88001 has no parentKey. Waiting card. Action held. It is not a screw.
  • 40100 is created only when one product group already stores 5637150105. The folder class decides screw or washer. No productType is sent.
  • The variant of 40100 is in the same batch, after that master, and is created only when the parentKey on 40100 resolved.
  • A variant of 88001 sent after that waiting card is held. It is not created under the card. It is applied when the card is placed.
  • A later row for 88001 with no parentKey updates the waiting card. It does not move it.

ON TEST POST /api/v1/product-release

Same as today once the variant exists: one row per variant and company. released: true adds the company. RH, RHU, ASW, and SPI also set shopOn true on that shop brick. Any other company is stored on the variant and has no shop brick. released: false removes the company and sets shopOn false. The brick stays. The hero image and the description stay. Logos sit on the company. A later released: true sets shopOn true on the same brick.

While the master is only a waiting card, the release is held. It is applied when the card is placed. After the variant exists, a company never sent is NOT_FOUND, retryable: companyCode … not found; send it on /companies first. With no variant and no waiting card: itemNumber not found; send the variant on /product-master first. Release does not place the product and does not create the variant.
lifecycleState is stored per company on the variant when released is true. "3" is accepted and still turns the shop on. The off switch is released: false, with no lifecycleState.
FieldRequiredRule
itemNumberYesThe variant number.
companyCodeYesA company already sent on /companies.
releasedYestrue or false.
lifecycleStateNoOn released: true: "1", "2", "3", or JSON null. Stored as sent for that company. null clears the stored state and leaves the shop as released set it. Omit the field and the stored state is left as it is. On released: false, leave the field out. That company’s stored state is removed with the company. Any other value fails the row and writes nothing. "3" does not mean the shop is off. To turn a shop off, send released: false.

Example

{
  "batchId": "a2-release-001",
  "items": [
    { "itemNumber": "40100", "companyCode": "RH",  "released": true,  "lifecycleState": "3" },
    { "itemNumber": "40100", "companyCode": "ASW", "released": true,  "lifecycleState": null },
    { "itemNumber": "40100", "companyCode": "RH",  "released": false }
  ]
}
  • These rows apply when variant 40100 exists. The same rows for waiting card 88001 are held and applied when that card is placed.
  • "3" is stored for RH. The RH shop still turns on, because released is true.
  • null is stored for ASW. The ASW shop still turns on.
  • The same row again, with the same state, comes back unchanged.
  • released: false for RH removes RH, sets shopOn false, keeps the hero image and the description, and removes the stored "3". ASW is left as it was.
  • "lifecycleState": "nope" fails that row with VALIDATION. The shop and the stored state are not changed.

ON TEST POST /api/v1/product-attributes

Same body as today. The attribute code must already be in the book from /attribute-definitions once the product exists. A code that is not in the book is ignored: is not in /attribute-definitions. The reply action is unchanged. Do not stop sending definitions, and send them before the values.

A waiting card with at least one attributeCode is held, one stored row per code. A newer row for the same code replaces it. The values are written when the card is placed. A row with no attribute list, and a product that is neither a catalogue item nor a waiting card, is NOT_FOUND, retryable: itemNumber not found; send it on /product-master first.

On a catalogue master or variant, a value whose group is not on that product’s folder is ignored, not failed: is not placed on a folder of this item. Null, "", or isDeleted: true clears a value. Do not resend the same row in a loop.

A row that sends categoryKey instead of itemNumber still looks up a catalogue folder by that folder’s own code. Approach 2 /tree does not create that folder, so a new category comes back NOT_FOUND: categoryKey not found; send it on /tree first. Sending /tree does not fix it. Folder defaults keep working only for folders that already exist from the earlier build.

There is no switch date and no agreed list of attributes to leave out. Until that list exists, keep the current send.

Link — not a call

There is no payload for the link. F&O does not send it.

  • A person types one category id on a PIM folder. The id is the same categoryKey text as /tree. The field name in PIM is the F&O category on that folder.
  • Do not put the same id on two product groups. /product-master then fails with CONFLICT and does not guess.
  • An id stored only on a folder above product group does not place a master. That row is VALIDATION.
  • Empty means that folder is not mapped. A child folder does not take its parent’s id. The id used for a product is the id on the folder the master sits in. PIM does not walk up.
  • Changing the id on a product group stores a link row: categoryKey, pimPath, layer productGroup. A rename, a move, or an unpublish that keeps the same id updates the path and sends nothing. Clearing the id deletes the table row and sends nothing.
  • A person moving a master onto a different id, or placing a waiting card into a folder that already has an id, stores {"itemNumber","categoryKey"}. The same id, no id, a move back to holding, a variant, and a /product-master save store nothing.
  • Both rows sit in fo_return_outbox. Neither has been posted.
  • The waiting folder is not mapped. Typing the id does not place waiting cards. Resend the master with that parentKey.
  • The save refusal is a second product group with the same id. The screen does not stop a person typing the id on a folder above product group. At switch 1 a master whose parentKey is stored only there fails VALIDATION.

The field is on TEST. TEST is switch 0, so parentKey is still the folder code. Do not assume TEST resolves parentKey through this field.

HELD, NOT POSTED PIM → F&O

One held row is one HTTP POST when the base URL, the header name, and the key are all set. The body is that row. Content-Type is application/json. The key travels in the one header you name. Each post also sends X-Outbox-Id and X-Saved-At. Timeout is 20 seconds. HTTP 2xx marks the row sent, and the body of that reply is not read. Any other status leaves the row held. A 401 stops that flush. There is no schedule. Nothing below has been posted.

A folder rename, move, unpublish, or publish is not one of these posts. Read it with GET /api/v1/fo-tree-links?page=1 and the same X-API-Key. One row per catalogue folder, 500 to a page, including a folder with no id and foMap false. The list is not filtered. The same folderId after a move is how a folder change is seen. POST /api/v1/fo-category-key writes the id back onto that folder.

Reads F&O calls

The variant field named itemNumber is empty on a master. categoryKey and foCategoryKey are the id on that master's product group, or an empty string. PIM does not walk up.

Reply shape — same envelope

HTTP 200 means the batch was read, including when failed is greater than 0. A failed row is inside results and errors. 413 the batch is too big and nothing in that call is applied. 401 bad key. Judge a row by its own results[] entry. /product-master does not answer unchanged.

FieldMeaning
oktrue only when failed is 0. A waiting card with action held, and a dependent row with action held, are successes.
results[].actioncreated · updated · held · unpublished · released · unreleased · unchanged · failed. unchanged is an attributes reply, not a product-master reply.
results[].codeOn a failure: VALIDATION, CONFLICT, or NOT_FOUND.
retryabletrue only when sending the same row later can succeed. A bad productType or a type change is not retryable. An unlinked parentKey is retryable after a person stores the id.
{
  "ok": false,
  "processed": 3,
  "failed": 1,
  "results": [
    { "key": "88001", "layer": "unassigned", "action": "held" },
    { "key": "88001-A", "action": "held",
      "note": "master 88001 is a waiting card; the row is stored and will be applied when it is placed" },
    { "key": "40100", "action": "failed", "code": "NOT_FOUND", "retryable": true,
      "error": "no PIM folder is linked to category 5637150105; a person must store it in F&O category on a product group" }
  ],
  "errors": [
    { "key": "40100", "code": "NOT_FOUND", "retryable": true,
      "error": "no PIM folder is linked to category 5637150105; a person must store it in F&O category on a product group" }
  ]
}

Decide a retry from code and retryable, not from the sentence in error. A waiting-card master also includes objectId and path. A held variant, translation, value, or release has no layer and no error. held is delivered. Do not retry it unless F&O changes it. The unlinked 40100 error above is the switch-1 reply.
